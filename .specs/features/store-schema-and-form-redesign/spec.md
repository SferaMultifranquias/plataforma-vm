# Spec — Store Schema and Form Redesign

## Modal Redesign Addendum

This iteration covers only create/edit store modal visual structure.

- approved target: attached image in current task
- scope: UI, responsive layout, accessibility, and selector preservation only
- modes: `Nova Loja` and `Editar Loja`
- mandatory section order: `Informações da Loja` -> `Identificação` -> `Localização` -> `Status` (edit only)
- preserved contract: `codigo`, `nome`, `marca`, `ativo`, `cidade`, `estado`
- preserved behavior: current Supabase insert/update paths, validation rules, toast flow, cache invalidation, authorization, and brand values
- exclusions: schema, migrations, Supabase config, API contracts, dependencies, remote writes, E2E

## Confirmed Current Schema (`public.lojas`)

```sql
create table public.lojas (
    id          bigint generated by default as identity primary key,
    codigo      text not null,
    nome        text not null,
    marca       text not null,
    ativo       boolean not null default true,
    created_at  timestamptz not null default now(),
    updated_at  timestamptz not null default now()
);

-- no columns for: cidade, estado, endereco, responsavel, telefone, email_contato
-- no migration ever added them
```

## Root Cause

The frontend CRUD (`stores-module.js:salvarLoja`) sends the following fields to `sb.from('lojas').insert(payload)` / `.update(payload)`:

- `codigo`, `nome`, `marca`, `ativo` — exist in schema ✓
- `endereco`, `cidade`, `uf`, `responsavel`, `telefone`, `email_contato` — **do not exist** in `public.lojas` ✗

Supabase rejects writes with unknown columns, surfacing the schema error via the platform toast. Endereco, responsavel, telefone, email_contato were never persisted — their data is permanently absent from the database. Cidade and uf were never persisted either, but their concept is valid and must be added via migration.

The table rendering (`stores-module.js:renderRow`) shows a `Responsável` column and reads `row.responsavel`, which is always `undefined` — the column has never existed.

## Final Store Contract (Frontend ↔ Database)

After the migration and frontend changes, the only fields sent and received are:

| Field | DB Column | Type | Required |
|-------|-----------|------|----------|
| `codigo` | `codigo` | `text` | yes |
| `nome` | `nome` | `text` | yes |
| `marca` | `marca` | `text` | yes |
| `ativo` | `ativo` | `boolean` | yes |
| `cidade` | `cidade` | `text` | no |
| `estado` | `estado` | `varchar(2)` | no |

## Obsolete Fields to Remove

Remove all frontend references to:

- `endereco`
- `responsavel`
- `telefone`
- `email` / `email_contato`

Remove database references (none exist, but confirm no lingering RLS policies or triggers reference them).

Remove the `Responsável` column from the stores table (header, row rendering, empty-state colspan, responsive/mobile rendering).

## Acceptance Criteria

### Create and Edit

1. User opens the store modal (create or edit).
2. Form renders with fields: `codigo`, `nome`, `marca`, `ativo`, `cidade`, `estado`.
3. `codigo`, `nome`, `marca` are required; client-side validation blocks submit with empty required fields.
4. `estado` input accepts exactly 2 uppercase characters.
5. Submit sends correct payload matching the contract above.
6. On success, toast confirms save, modal closes, table refreshes.
7. On error (e.g. duplicate `codigo`), toast shows the server error.

### Edit Hydration

1. Existing values for all 6 fields are correctly populated into form inputs.
2. Fields that were `null` in the database render empty inputs.
3. `estado` displays the stored value in uppercase.

### Responsive and Visual

1. Desktop (≥768px): two-column layout for form fields.
2. Mobile (<768px): single-column layout.
3. No horizontal overflow in the modal at any viewport width.
4. Form uses shared platform CSS classes (`.form-input`, `.form-select`, `.form-label`, `.btn-primary`, `.btn-secondary`).
5. Modal follows the platform design system (consistent padding, border-radius, overlay, animation).

### Validation Rules

| Field | Rule | Message |
|-------|------|---------|
| `codigo` | required, max 10 chars | "Código é obrigatório" |
| `nome` | required, max 100 chars | "Nome da loja é obrigatório" |
| `marca` | required, must be one of `[O Boticario, QDB]` | "Selecione uma marca" |
| `cidade` | optional, max 50 chars | — |
| `estado` | optional, exactly 2 uppercase letters | — |

### Migration and Compatibility

1. Migration is additive only — no existing data is altered or dropped.
2. Old rows remain valid after migration (both `cidade` and `estado` are nullable).
3. Data-completion for existing rows is a separate, non-blocking step.
4. Rollback is a single `DROP IF EXISTS` statement for the two added columns.
5. No existing RLS policies, triggers, or indexes reference the removed fields (confirm during investigation).
